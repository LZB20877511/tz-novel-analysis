## 它和别的"小说 AI 工具"有什么不同？

市面上绝大多数网文工具在解决**"读之前帮你筛书"**：
榜单聚合、题材热度、推荐排序。

这个项目解决的是另一件事——**"读完之后，怎么给出一个站得住脚的判断"**。

| | 常见工具 | TZ Novel Analysis |
|---|---|---|
| 是否读原文 | ❌ 只读榜单/简介/评论 | ✅ **必须读真实正文** |
| 评价来源 | 聚合别人的评论 | **模型自评 + 外部共识，双轨并列** |
| 分歧处理 | 取平均 / 只报一个分 | **保留分歧，差异 ≥1.5 分必须单列** |
| 覆盖度 | 通常不说 | **强制披露：读了几章、占全书百分之几** |
| 剧透 | 不管 | **硬闸门：结局、反转、配对一律不出现在简介里** |
| 可复核性 | 无法查证 | **每条判断带证据标签 + 逐字原文** |

> **一句话区别**：它们告诉你"别人觉得好不好"；这个项目告诉你"我读完觉得怎样，证据在哪，你可能为什么会不同意"。

## 三个自研模块（都不是拍脑袋定的）

### 1️⃣ 叙事人称判定 — `tznovel person`

**为什么需要它**：题材对得上的书，可能有六成是第一人称。人工逐本读开头，成本高。

**做法**：剔除对话后，统计叙述句中以「我」作主语的比例。

```
第三人称：《茅山后裔》0.1%  《走进修仙》0.1%
第一人称：《民调局异闻录》后传  27.5% – 36.4%
阈值 15% —— 两侧余量都很大，不是硬凑的
```

```bash
$ tznovel person examples/茅山后裔_样本.json
  叙述句 988 句，其中以「我」作主语 1 句
  占比   0.1%
  判定   第三人称（置信度 高）
```

### 2️⃣ 题材前提验证 — `tznovel premise`

**为什么需要它**：网上所有题材标签都是人填的，**没人验证**。实测三次翻车：

| 号称 | 实际 |
|---|---|
| 《走进修仙》"都市→修仙" | 现代段仅 **93 字**，在第 1000 字之后，实为**开局即仙侠** |
| 《民调局异闻录》"第三人称" | 正文通篇**第一人称**（"我叫沈辣"） |
| 《修真聊天群》"有跃迁" | 都市与修真界**并存**，从不离开都市 |

```bash
$ tznovel premise examples/茅山后裔_样本.json
  现代词 95 次（1.39/千字）｜修行词 72 次（1.05/千字）
  现代词占比 56.9%
  首次现代词位置 210 ｜ 首次修行词位置 7033
  跃迁判定：都市与修行并存（未退出都市）
```

### 3️⃣ 文风量化 — `tznovel stats`

把"文笔好不好"拆成可数的东西：句长、段长、对话占比、标点密度、手法词频。

**⚠️ 它只报数，不下判断。** 指标交给评审者解释。

```
平均句长 31.9 字 ｜ 段落均长 84.4 字
对话字数占比 30.4% ｜ 「！」5.3/千字 ｜ 「？」5.5/千字
廉价转折 A 组 68 次（忽然48 简直11 顿时6 陡然3）
廉价转折 B 组 55 次（竟然42 猛然6 不由5）
★ 问号 > 感叹号 —— 少见的叙述指纹（反问式幽默 / 克制叙述）
```

**为什么要分 A/B 两组**：只报 A 组（忽然/顿时/陡然）会给人"毫无模板感"的错觉，
而 B 组（竟然/居然/不由）常常才是真实的惰性指纹。**两组都要看。**

## 快速开始

```bash
pip install tznovel
```

或者从源码：

```bash
git clone https://github.com/LZB20877511/tz-novel-analysis.git
cd tz-novel-analysis
pip install -e ".[dev]"
```

### 跑一下

```bash
# 人称判定
tznovel person examples/茅山后裔_样本.json

# 文风量化
tznovel stats examples/茅山后裔_样本.json --json-out stats.json

# 题材验证
tznovel premise examples/茅山后裔_样本.json

# 抓取单页并提取正文（自动 UA 降级）
tznovel fetch "https://example.com/chapter/1.html" --preview

# 源可达性探测（批量）
tznovel probe url1 url2 url3

# 报告送审前自检
tznovel check report.md --strict
```

### 作为库使用

```python
from tznovel import analyze_text, detect_person, check_premise

chapters = [{"label": 1, "title": "第一章", "body": open("ch1.txt").read()}]

# 人称
v = detect_person(chapters)
print(v.verdict, v.ratio_pct)          # 第三人称 0.1

# 文风
r = analyze_text(chapters)
print(r.avg_sent, r.dlg_char_pct)      # 31.9 30.4
print(r.cheap_a_total, r.cheap_b_total)  # 68 55

# 题材
p = check_premise(chapters)
print(p.transition)                     # 都市与修行并存（未退出都市）
```

## 抓取层：错误分类驱动降级

**核心经验：403 不等于要用重型武器。**

实测同一个章节页：

```
PC UA (Chrome 126)  →  HTTP 403 ，响应体 "403 Forbidden nginx"
移动 UA (iPhone)     →  HTTP 200 ，23024 字正文
```

诊断：响应头 `Server: cloudflare` + `cf-cache-status: BYPASS`，
说明这是 **WAF 按 UA 判定的规则**，不是 Cloudflare JS 挑战。
**换 UA 就过，不需要任何浏览器自动化。**

因此降级顺序按"成本从低到高"设计：

```
1. PC UA 直取
2. 换移动 UA（最有效，实测解决问题）
3. 退避重试（应对 5xx / 偶发超时）
4. 判定为站点无内容 → 直接换源（不要浪费轮次）
```

### 错误分类

| 类型 | 判据 | 动作 |
|---|---|---|
| `FATAL` | 404 / 410 / 451 | 换源 |
| `EMPTY_SITE` | 页面含「转码失败」等 | **换源，爬虫再强也没用** |
| `IP_BLOCKED` | 403 + 拦截特征 | 换 UA / 换 IP |
| `RATE_LIMIT` | 429 | 降频重试 |
| `RETRYABLE` | 5xx | 退避重试 |
| `ENCODING_BAD` | 首行乱码 / U+FFFD 高 | 重抓 |

### 一个容易踩的坑：pua 低 ≠ 正文干净

某站页面混入 1 个非法字节，整章被当 GBK 解码 → **全乱码**，
而 `pua` 只报 **5%**。按"pua>50 才判字体加密"的旧阈值，会误判为"轻度可用"。

**本项目的解码策略**：先宽松 UTF-8 → 检查 U+FFFD 占比 >2% 才试 gb18030 → 并抽验首行是否可读。
**绝不"抛异常就整体换编码"**（那正是整章乱码的成因）。

## 报告自检：把能程序的错误交给程序

实测发现有三类错误**每次都会发生**，且都程序能查：

| 检查 | 内容 | 实测 |
|---|---|---|
| **C1 简介字数** | ≤120 且自标值=实际值 | **手工估了 4 次，4 次全错且全部少报** |
| **C2 剧透扫描** | 结局/反转/凶手正则 | — |
| **C3 同句重复** | 危险表述出现 ≥2 次即报 | **连续 3 份报告栽在这里** |
| **C4 加权核算** | 六维加权精确值 vs 文中声称 | 曾出现 5.90 vs 实际 5.85 |
| **C5 必备结构** | 结论/简介/覆盖度/证据标签 | — |
| **C6 不实陈述** | 草稿声称"已过闸门"即 FAIL | 曾把"未审"写成了"已过" |

```bash
$ tznovel check draft.md --strict
[FAIL] C1 简介字数：自标 97 实际 99（差 2）—— 实测 4/4 份报告都在此出错
[PASS] C4 加权核算：= 6.90
汇总：1 FAIL / 0 WARN / 5 PASS
```

## 六维评分（可选，供需要量化时使用）

| 维度 | 权重 | 含义 |
|---|---|---|
| 文笔文风 W | 0.25 | 句法、用词、节奏 |
| 人物描写 C | 0.20 | 动机自洽、是否工具人 |
| 事物描写 T | 0.15 | 场景/设定/物品的描写功力 |
| 感情描写 E | 0.15 | 含亲情/友情/信念，不只爱情 |
| 情节节奏 P | 0.15 | 结构、伏笔、张弛 |
| 阅读体验 X | 0.10 | 上手门槛、沉浸感、收尾满意度 |

**双轨制**：模型自评（主，决定排序）+ 外部共识（对照）。
**差异 ≥1.5 分必须单列分歧说明，禁止取中间值抹平。**

## 合规边界（请务必阅读）

本项目是**个人阅读分析工具**，不是阅读器。

| ✅ 做 | ❌ 不做 |
|---|---|
| 分析**已公开可免费阅读**的章节 | 绕过付费墙 / VIP 章节 |
| 抽样阅读（数章，用于分析） | 批量下载整本书并分发 |
| 抓取公开榜单、元数据 | 破解验证码 |
| 本地个人分析 | 二次分发正文内容 |

**本项目仓库中不包含任何小说正文。** `examples/` 下的样本仅用于演示分析功能，
来源为公开转载页，**请勿用于任何形式的再分发**。

请遵守目标站点的 robots 协议与版权法规。**使用本项目产生的任何后果由使用者自行承担。**

## 方法论：为什么不给你一个"总分"

因为**总分是最没用的信息**。

一本书 6.8 分意味着什么？可能文笔 5 分情节 8 分，也可能全都 6.8 分——
**这两本书完全不同，但对你的价值天差地别**。

所以本项目坚持：

1. **给分项，不给单一总分**（或只在分项之后才给）
2. **分歧不抹平**——两派在吵什么，比平均几分有用
3. **必须写缺陷**——只写优点的分析视为不合格
4. **必须写覆盖度**——读了 3 章就说 3 章
5. **必须能复核**——每条判断挂证据标签与逐字原文

详见 [`docs/`](docs/) 目录。
