## 它和别的"小说 AI 工具"有什么不同？

市面上绝大多数网文工具在解决**"读之前帮你筛书"**：
榜单聚合、题材热度、推荐排序。

这个项目解决的是另一件事——**"读完之后，怎么给出一个站得住脚的判断"**。

| | 常见工具 | TZ Novel Analysis |
|---|---|---|
| 是否读原文 | ❌ 只读榜单/简介/评论 | ✅ **必须读真实正文** |
| 评价来源 | 聚合别人的评论 | **模型自评 + 外部共识，双轨并列** |
| 分歧处理 | 取平均 / 只报一个分 | **保留分歧，差异 ≥1.5 分必须单列** |
| 覆盖度 | 通常不说 | **强制披露：读了几章、占全书百分之几** |
| 剧透 | 不管 | **硬闸门：结局、反转、配对一律不出现在简介里** |
| 可复核性 | 无法查证 | **每条判断带证据标签 + 逐字原文** |

> **一句话区别**：它们告诉你"别人觉得好不好"；这个项目告诉你"我读完觉得怎样，证据在哪，你可能为什么会不同意"。

## 三个自研模块（都不是拍脑袋定的）

### 1️⃣ 叙事人称判定 — `tznovel person`

**为什么需要它**：题材对得上的书，可能有六成是第一人称。人工逐本读开头，成本高。

**做法**：剔除对话后，统计叙述句中以「我」作主语的比例。

```
第三人称：《茅山后裔》0.1%  《走进修仙》0.1%
第一人称：《民调局异闻录》后传  27.5% – 36.4%
阈值 15% —— 两侧余量都很大，不是硬凑的
```

```bash
$ tznovel person examples/茅山后裔_样本.json
  叙述句 988 句，其中以「我」作主语 1 句
  占比   0.1%
  判定   第三人称（置信度 高）
```

### 2️⃣ 题材前提验证 — `tznovel premise`

**为什么需要它**：网上所有题材标签都是人填的，**没人验证**。实测三次翻车：

| 号称 | 实际 |
|---|---|
| 《走进修仙》"都市→修仙" | 现代段仅 **93 字**，在第 1000 字之后，实为**开局即仙侠** |
| 《民调局异闻录》"第三人称" | 正文通篇**第一人称**（"我叫沈辣"） |
| 《修真聊天群》"有跃迁" | 都市与修真界**并存**，从不离开都市 |

```bash
$ tznovel premise examples/茅山后裔_样本.json
  现代词 95 次（1.39/千字）｜修行词 72 次（1.05/千字）
  现代词占比 56.9%
  首次现代词位置 210 ｜ 首次修行词位置 7033
  跃迁判定：都市与修行并存（未退出都市）
```

### 3️⃣ 文风量化 — `tznovel stats`

把"文笔好不好"拆成可数的东西：句长、段长、对话占比、标点密度、手法词频。

**⚠️ 它只报数，不下判断。** 指标交给评审者解释。

```
平均句长 31.9 字 ｜ 段落均长 84.4 字
对话字数占比 30.4% ｜ 「！」5.3/千字 ｜ 「？」5.5/千字
廉价转折 A 组 68 次（忽然48 简直11 顿时6 陡然3）
廉价转折 B 组 55 次（竟然42 猛然6 不由5）
★ 问号 > 感叹号 —— 少见的叙述指纹（反问式幽默 / 克制叙述）
```

**为什么要分 A/B 两组**：只报 A 组（忽然/顿时/陡然）会给人"毫无模板感"的错觉，
而 B 组（竟然/居然/不由）常常才是真实的惰性指纹。**两组都要看。**

## 运行环境

**两层，可以分开用：**

| 层 | 是什么 | 需要什么 |
|---|---|---|
| **① Python 工具包** `tznovel` | 文风量化 / 人称判定 / 题材验证 / 报告自检 | **只要 Python 3.9+ 和 requests** |
| **② Agent 协作模型** `agents/` + `docs/data/SOP.md` | 多角色分工跑完整分析流程 | 支持多 Agent 协作的宿主 |

### 关于 ①：几乎零门槛

| 项 | 要求 |
|---|---|
| Python | 3.9 / 3.10 / 3.11 / 3.12（CI 三系统 × 四版本验证） |
| 操作系统 | Windows / macOS / Linux |
| 依赖 | **仅 `requests`**，无 Pandas / NumPy / 浏览器驱动 |
| 网络 | **只有 `fetch` 命令需要**，纯分析完全离线 |

**不需要**：GPU ｜ 大模型 API Key ｜ 浏览器/Playwright ｜ 数据库 ｜ 任何账号

> 这是刻意设计——**分析结论必须可复现**。同一输入，谁跑都得同一个数字，
> 否则"证据"就失去意义。所以所有分析都是**确定性算法**，零网络推理调用。

### 关于 ②：Agent 层是可选的

`agents/` 下有 6 个角色卡（书目定位 / 章节速读 / 评论取证 / 独立评论 / 防剧透审校 / 寻书猎手），
它们通过**落盘文件交接**，不靠对话上下文传递。

**宿主不支持多 Agent 也完全能跑** —— 按顺序自己充当每个角色即可。
多 Agent 的价值只是并行提速，以及让"自评"与"读外部评论"发生在不同上下文里（避免污染）。

## 分析你自己手上的书

**大多数人的实际用法是这个：手上有一本 txt（或几段复制来的文字），想知道它什么水平。**

### 支持两种输入

**① 纯文本文件（最简单）**

把小说存成 `.txt`，直接传进去：

```bash
tznovel person  我的小说.txt      # 人称判定
tznovel stats   我的小说.txt      # 文风量化
tznovel premise 我的小说.txt      # 题材验证
```

> **整本书塞一个 txt 也行**，但工具会把它当"1 章"处理。
> 想按章统计（推荐），用方式 ②。

**② JSON 章节数组（按章统计，信息更全）**

```json
[
  {"label": 1, "title": "第一章", "body": "正文内容..."},
  {"label": 2, "title": "第二章", "body": "正文内容..."}
]
```

```bash
tznovel stats 我的小说.json --json-out 结果.json
```

**字段说明**：`label`（章号，可省）、`title`（章名，可省）、`body`（正文，必填）。
外层也可以是 `{"chapters": [...]}`。

### 一段最简单的 Python 脚本：txt → 分章 → 分析

```python
import json
from pathlib import Path
from tznovel import analyze_text, detect_person

# 按"第X章"切分（你可以换成自己书的章节标记）
raw = Path("我的小说.txt").read_text(encoding="utf-8")
parts = raw.split("第")           # 粗略切分
chapters = [{"label": i + 1, "body": ("第" + p) if i else p}
            for i, p in enumerate(parts) if p.strip()]

print("章数:", len(chapters))
print("人称:", detect_person(chapters).verdict)
r = analyze_text(chapters)
print(f"总字数 {r.total_chars}，平均句长 {r.avg_sent}")
```

### 分析结果怎么读

| 指标 | 含义 | 参考 |
|---|---|---|
| 平均句长 | 30 字左右属正常；>45 偏长，读着累 | 实测 6 本：28.5–48.9 |
| 对话字数占比 | 10% 以下偏叙述，35% 以上偏对白 | 实测 10.1%–37.5% |
| 「！」/千字 | 越高情绪越外放 | 实测 2.95–10.48 |
| 廉价转折 A/B | 两组都要看，只报 A 组会误判 | 见 [方法论](docs/METHODOLOGY.md) |

> ⚠️ **工具只报数，不下判断。** 这些指标要结合题材看 ——
> 军事文句长 48 字是正常的，轻小说 48 字就太沉重了。

## 抓取层：错误分类驱动降级

**核心经验：403 不等于要用重型武器。**

实测同一个章节页：

```
PC UA (Chrome 126)  →  HTTP 403 ，响应体 "403 Forbidden nginx"
移动 UA (iPhone)     →  HTTP 200 ，23024 字正文
```

诊断：响应头 `Server: cloudflare` + `cf-cache-status: BYPASS`，
说明这是 **WAF 按 UA 判定的规则**，不是 Cloudflare JS 挑战。
**换 UA 就过，不需要任何浏览器自动化。**

因此降级顺序按"成本从低到高"设计：

```
1. PC UA 直取
2. 换移动 UA（最有效，实测解决问题）
3. 退避重试（应对 5xx / 偶发超时）
4. 判定为站点无内容 → 直接换源（不要浪费轮次）
```

### 错误分类

| 类型 | 判据 | 动作 |
|---|---|---|
| `FATAL` | 404 / 410 / 451 | 换源 |
| `EMPTY_SITE` | 页面含「转码失败」等 | **换源，爬虫再强也没用** |
| `IP_BLOCKED` | 403 + 拦截特征 | 换 UA / 换 IP |
| `RATE_LIMIT` | 429 | 降频重试 |
| `RETRYABLE` | 5xx | 退避重试 |
| `ENCODING_BAD` | 首行乱码 / U+FFFD 高 | 重抓 |

### 一个容易踩的坑：pua 低 ≠ 正文干净

某站页面混入 1 个非法字节，整章被当 GBK 解码 → **全乱码**，
而 `pua` 只报 **5%**。按"pua>50 才判字体加密"的旧阈值，会误判为"轻度可用"。

**本项目的解码策略**：先宽松 UTF-8 → 检查 U+FFFD 占比 >2% 才试 gb18030 → 并抽验首行是否可读。
**绝不"抛异常就整体换编码"**（那正是整章乱码的成因）。

## 报告自检：把能程序的错误交给程序

实测发现有三类错误**每次都会发生**，且都程序能查：

| 检查 | 内容 | 实测 |
|---|---|---|
| **C1 简介字数** | ≤120 且自标值=实际值 | **手工估了 4 次，4 次全错且全部少报** |
| **C2 剧透扫描** | 结局/反转/凶手正则 | — |
| **C3 同句重复** | 危险表述出现 ≥2 次即报 | **连续 3 份报告栽在这里** |
| **C4 加权核算** | 六维加权精确值 vs 文中声称 | 曾出现 5.90 vs 实际 5.85 |
| **C5 必备结构** | 结论/简介/覆盖度/证据标签 | — |
| **C6 不实陈述** | 草稿声称"已过闸门"即 FAIL | 曾把"未审"写成了"已过" |

```bash
$ tznovel check draft.md --strict
[FAIL] C1 简介字数：自标 97 实际 99（差 2）—— 实测 4/4 份报告都在此出错
[PASS] C4 加权核算：= 6.90
汇总：1 FAIL / 0 WARN / 5 PASS
```

## 方法论：为什么不给你一个"总分"

因为**总分是最没用的信息**。

一本书 6.8 分意味着什么？可能文笔 5 分情节 8 分，也可能全都 6.8 分——
**这两本书完全不同，但对你的价值天差地别**。

所以本项目坚持：

1. **给分项，不给单一总分**（或只在分项之后才给）
2. **分歧不抹平**——两派在吵什么，比平均几分有用
3. **必须写缺陷**——只写优点的分析视为不合格
4. **必须写覆盖度**——读了 3 章就说 3 章
5. **必须能复核**——每条判断挂证据标签与逐字原文

详见 [`docs/`](docs/) 目录。
